## 0. 文档结论

项目采用“同一品牌、账号和大厅，一套 UGC 创作与联机底座，两个按需资源玩法频道”的产品结构。两个玩法的可信 GDScript 随基础客户端发布，按需模块只能下发平台资源、官方内容和 UGC 数据，禁止远程下发玩法代码。

1. **玩法一《机关狂奔》（代号 TRAPRUSH）**：轻动作竞速。玩家利用道具穿越、规避或击毁障碍，并通过支持上下层、左右区块互联的传送网络完成多路线竞速。
2. **玩法二《双塔要塞》（代号 BASTION）**：低动作塔防对战。双方先在赛前编辑阶段为对手布置受预算约束的障碍，随后在运行阶段搭建和升级自己的炮塔体系，承受完全镜像的系统波次并争取让己方核心存活更久。

两个玩法共享以下底座：

- `SharedContracts`：稳定 ID、Schema、命令、事件、快照协议；
- `SimulationCore`：纯数据、固定 Tick 的权威仿真；
- `UGCRuntime`：白名单 Archetype、版本化规则字节码解释器、gas 预算；
- `CreatorTools`：共用编辑器外壳、玩法专用工具面板、EditCommand、Undo/Redo、独立持续 Preview；
- `ContentPlatform`：验证、构建、签名、自动公开、热发布和回滚；
- `MatchServer`：一局一 Godot Headless 进程、服务器权威、命令校验、快照同步和回放；
- `ControlPlane`：TypeScript + Fastify、SQLite、Content Registry、Matchmaker 与结果接收；
- `RealtimeGateway`：独立 TypeScript TLS WebSocket 网关；
- `MatchHost`：启动、限额、续租和回收每场 MatchServer；
- AI 主导、人类监督纠偏的开发流程。

开发顺序固定为：

```text
最小 Monorepo 与共享底座
  → TRAPRUSH 纵向切片
  → Edit / Preview / Hot Publish 闭环
  → BASTION 复用底座形成第二个纵向切片
  → 移动端适配
  → 网页 / 微信小游戏减配
  → 鸿蒙 NEXT 二期评估
```

一期不建设复杂排位、赛季、观战、跨区和弹性扩容。香港长期测试环境固定按 50 CCU 设计，容量满时进入 FIFO 队列。排名只存在于单局结算中；离线单人可以试玩，但任何离线成绩、奖励和结算不得回写在线账户。

本版本不再承诺固定 16 周。开发按里程碑和退出条件顺序推进，由唯一人类负责人签署玩法清单；AI 和机器人只能提供证据，不能替代主观玩法验收。

# 第一部分：项目立项与范围

## 1. 项目愿景

打造一个适合 AI 主导开发、支持快速创作和快速验证的轻 3D UGC 游戏底座。玩家既可以游玩官方和社区内容，也可以通过低门槛 Edit 模式修改地图、机关、障碍、路径、炮塔槽位和有限规则，并在很短时间内进入单人或多人测试。

项目不追求首版就成为通用游戏创作平台。第一版只验证四件事：

1. 两个差异明显的玩法能否复用同一套仿真、内容和发布底座；
2. 创作者能否在不写代码的情况下做出可玩的玩法变体；
3. 从修改内容到进入多人测试是否足够快；
4. AI 能否在严格规则和自动化测试约束下承担大部分实现工作。

## 2. 已拍板决策

以下事项在 v0.2 中视为锁定。完整决策追踪见附录 D；明确列入“开发期决策清单”的事项除外：

1. 玩法采用轻动作竞速和低动作塔防对战两条线；
2. 一期无账号级排位、MMR、段位和赛季，只做单局内名次或 MVP 结算；
3. 允许离线单人试玩，但离线成绩、奖励、战绩和解锁不回写在线服务；
4. 一期单区、固定容量，不做自动扩缩容、跨区和观战；
5. 主机平台暂不考虑；
6. 必须提供方便的 Edit 模式，并支持快速修改、预览、热发布和安全热生效；
7. TRAPRUSH 以道具、避障、障碍破坏和立体传送移动为核心；BASTION 以赛前互设障碍、赛中搭建炮塔体系为核心；
8. 开发方式为 AI 主导，人类负责目标、逐任务审查、纠偏和高风险决策；
9. 开发者以桌面原生客户端和 Headless 为主，测试者优先使用 Web 链接；共享功能持续通过 Web 兼容门禁；
10. Web 支持游玩和轻量编辑；桌面安装版提供完整规则图；Android/iOS 一期只游玩、评分和管理内容；
11. 两个玩法共用编辑器框架，通过玩法 Schema、验证器和专用工具面板扩展；
12. 一期线上环境位于腾讯云香港，仅有“本地 + 长期测试”两个长期环境；不存在正式 Production；
13. 一期所有实时客户端统一使用 WebSocket；控制面使用 JSON，实时对局使用版本化二进制 Schema；
14. `SimulationCore` 使用 64 位整数承载的定点数和确定性执行顺序，不以 Godot 浮点物理作为裁决依据；
15. 一场对局一个 Godot Headless 进程，由 MatchHost 管理并经独立 WebSocket 网关接入；
16. 控制面一期以 SQLite 起步且仅 Fastify 可直接访问，PostgreSQL 为后续迁移目标；
17. 公开 UGC 只允许平台资产与结构化内容，技术验证通过后在测试环境自动公开，不做人工前置审核；
18. 一期人类团队按一名核心负责人设计，路线图按里程碑而非固定周数推进。

## 3. 一期范围

### 3.1 一期必须完成

- Godot 4 Standard + GDScript 项目骨架；
- 桌面客户端与 Godot Headless 权威服；
- TRAPRUSH 可完整游玩的线上纵向切片；
- BASTION 可完整游玩的最小纵向切片；
- 共用的游戏内 Edit 模式；
- Web 轻量 Edit、桌面完整 Edit，以及共享编辑器框架；
- `EditCommand → Validate → Preview → Publish` 完整链路；
- UGC 基础内容不可变版本、签名、P0/P1 运行时补丁序列和回滚；
- 单局排名与结算；
- 离线单人试玩；
- 香港区 50 CCU、FIFO 排队的固定容量部署模型；
- Fastify 控制面、SQLite、COS、独立 WebSocket 网关与 MatchHost；
- AI 工作规则、测试门禁和变更审计；
- 每个 PR 的公开临时 Web 沙盒预览；
- PC/Steam、Android、iOS 的工程预留与基本导出验证。

### 3.2 一期明确不做

- 账号级天梯、MMR、段位、赛季和赛季奖励；
- 离线成绩回写；
- 观战、录像播放 UI、跨区匹配；
- 自动弹性扩容；
- 主机平台；
- 鸿蒙 NEXT；
- 玩家上传任意 GDScript、C#、GDExtension、PCK；
- 玩家上传自定义 3D 模型、音频和任意贴图；
- 实时多人协同编辑和 CRDT；
- 公开 UGC Fork；
- 任意脚本语言或任意公式编辑；
- 高速弹道、复杂命中回溯；
- 复杂局外经济、抽卡和付费数值系统；
- 微信小游戏与原生端完全同画质、同包体；
- 手柄、本地同屏、移动端编辑器与 Web 离线试玩；
- 评论、聊天、语音、Ping 和自由文本 UGC 标题/简介；
- 个性化内容推荐；
- 无障碍专项门禁；
- 开发期间的外部真人玩法测试；
- 正式 Production、主动监控告警与备份恢复。

## 4. 目标平台与技术边界

| 平台 | 计划 | 技术策略 |
|---|---|---|
| PC / Steam | 一期主开发平台 | Windows 优先；键鼠游玩；完整 Edit 与规则图；GodotSteam 在共享核心与 Web 闭环稳定后接入 |
| Android | 一期导出验证 | Compatibility、触控游玩、评分和内容管理；不提供 Edit |
| iOS | 一期导出验证 | Compatibility、触控游玩、评分和内容管理；使用 Mac + Xcode/TestFlight |
| 网页 | 一期持续测试入口 | Windows/macOS 的 Chrome、Edge 最新两个大版本；游玩 + 轻量 Edit；必须联网 |
| 微信小游戏 | 一期后跟进 | Web 导出 + 社区适配层；共享规则，只降低资源与效果 |
| 鸿蒙 NEXT | 二期 | 等待并评估 OpenHarmony 社区移植成熟度 |
| 主机 | 不考虑 | 不投入输入、美术或发行适配成本 |

客户端固定使用 **Godot 4 Standard + GDScript**。工程中禁止引入 `.cs`、`.csproj` 和 Godot .NET 运行时，以保留 Web/微信小游戏导出路径。

渲染以 **Compatibility / WebGL 2** 为共同基线。PC 可以有 Forward+ 增强配置，但任何核心可读性和玩法反馈不得依赖 Forward+ 专属效果。

共享玩法、编辑器和仿真核心禁止依赖 GDExtension。原生平台适配层可在有 Web 空实现且不改变共享玩法语义时例外使用，例如后续 GodotSteam 适配。

### 4.1 产品表现与设备基线

- 美术：统一风格化低多边形、清晰纯色分区和少量描边；两个玩法通过主题和色板区分；
- 语言：一期同时支持简体中文和英文，所有 UI 与系统文本从第一天使用本地化键；
- 目标年龄：青少年及成人，按 12+/13+ 设计，不主动面向低龄儿童；
- 商业化：一期不做广告、内购、付费货币、皮肤商业接口或创作者分成，也不预埋相关玩法钩子；
- 无障碍：原型期不设按键重映射、色盲、屏幕阅读或镜头震动开关等专项门禁；
- 最低设备参考：Windows 10/11 集显与 8 GB 内存、Android 10/4 GB 中端机、iPhone XR/SE2、桌面 WebGL 2；
- 帧率观察目标：PC/桌面 Web 60 FPS，移动最低 30 FPS，高档移动设备可选 60 FPS；
- 分发签名：Windows 测试包暂不购买代码签名；Android 使用测试/发布 keystore；iOS 遵循 TestFlight 签名要求。

# 第二部分：共用产品结构

## 5. 产品入口

首版是同一品牌、账号和大厅下的模块化产品。两个玩法代码随基础客户端发布，首次进入频道时再按需下载该玩法的可信资源、官方内容和 UGC 数据：

```text
主大厅
├─ 机关狂奔
│  ├─ 快速游戏
│  ├─ 房间码
│  ├─ 单人试玩
│  └─ 关卡编辑（桌面完整 / 桌面 Web 轻量）
├─ 双塔要塞
│  ├─ 快速游戏
│  ├─ 房间码
│  ├─ 单人对 AI
│  └─ 蓝图编辑（桌面完整 / 桌面 Web 轻量）
├─ 我的内容
│  ├─ 草稿
│  ├─ 已发布版本
│  └─ 内容管理
├─ 公共内容
│  ├─ 最新
│  ├─ 评分
│  ├─ 游玩次数
│  └─ 已验证
└─ 设置
```

一期不做个性化推荐和创作者商业化。公共内容使用四个固定标签页；机器人或真人尚未完成过的内容仍可公开，但标记“未验证可完成”，且不进入默认“已验证”筛选。内容名称由系统或预设词库组合，说明只使用结构化标签。

平台不自动对“最新”列表做内容哈希去重、作者折叠或占比限制；刷屏由管理员手动清理。此策略属于已接受风险，不代表具备公共内容治理能力。

## 6. 账号、在线与离线规则

### 6.1 在线模式

- 服务端是唯一权威；
- 玩家只提交输入和操作意图；
- 单局结构化记录写入后端用于调试和遥测，但客户端不提供历史战绩、累计胜率或长期排名页面；
- 单局内产生名次、胜负、MVP 和统计面板；
- 不计算或展示长期段位；
- UGC 内容必须为平台验证并签名的版本；
- TRAPRUSH 在线房允许 1～8 名真人直接开始，单人在线也走 MatchServer；
- BASTION 只按蓝图声明的合法真人阵容开始；
- 在线房不自动补机器人。

正式账号与 Guest 规则：

- 匿名用户获得浏览器绑定的 Guest ID 和本地恢复密钥；
- Guest 草稿自动保存云端并保留本地缓存，云端保留 30 天；
- 发布和跨设备访问必须注册登录并认领草稿；
- 一期使用用户名 + 密码，任何互联网用户都可注册；
- 不提供邮箱验证、密码找回、CAPTCHA、IP 限频或设备约束；
- 忘记密码只能注册新账号，旧账号和内容不迁移；
- 注册用户名直接作为公开玩家名与作者名，不做文本过滤；
- 一期不提供文字、语音、快捷短语或 Ping。

上述开放注册、公开用户名和零防滥用组合风险很高，只适用于当前长期测试环境，不能表述为正式公开运营能力。

### 6.2 离线单人模式

- 使用与线上相同的 `SimulationCore` 和内容格式；
- 通过本地内嵌权威仿真运行，不接受外部客户端结果；
- 可游玩官方内容、已缓存的签名 UGC 和本地草稿；
- 可保存本地设置、编辑草稿和个人试玩记录；
- 不回写在线成绩、奖励、战绩、排名和解锁；
- UI 必须持续显示“离线试玩，成绩不上传”；
- 恢复在线后不得补传离线结算；
- 离线试玩只保证 PC、Android 和 iOS 安装版；Web 必须联网，但断网时需保住本地草稿缓存；
- TRAPRUSH 可记录本机最佳命令轨迹并播放无碰撞幽灵，不下载他人幽灵；
- BASTION 使用模板机器人按预算布障并以规则化策略建塔。

### 6.3 单局排名

一期的“排名”只指当前对局结算：

- TRAPRUSH 实际按本局 1～8 人结算；默认按冲线顺序，也允许受限规则组合定义结束条件；
- BASTION：先按胜负分队，再按队内贡献给出 MVP 顺序；
- 未完成玩家按检查点进度、距下一目标的合法路径距离和到达时间排序；
- 非法命令被拒绝并记日志，但一期不因作弊或异常主动踢出、封禁；
- 结算结果不生成 MMR，不影响下一局匹配权重。

### 6.4 数据保留、遥测与可靠性

- 结构化对局记录 90 天、回放 30 天、详细日志 14 天、崩溃与安全事件 180 天、匿名草稿 30 天；
- 使用伪匿名 ID 采集玩法、性能、错误和发布指标；
- 玩家可退出非必要玩法分析，但不能退出安全、结算和故障日志；
- 一期不做数据库或 COS 备份，云端草稿、内容、评分与记录都可能永久丢失；
- 云端保存属于便利功能，不构成可靠存储承诺；
- 保留周期只是正常状态下的最长保存期限，不构成持久性、RPO 或 RTO 承诺；版本回滚也以旧 Bundle、签名和 Registry 仍可读取为前提；
- 一期只保存日志，不建设仪表盘、可用性探测或主动告警。

## 7. 共同 UGC 原则

UGC 是数据，不是代码。两个玩法共享同一套草稿、EditCommand、历史、Preview 和发布外壳；玩法模块只注册自己的 Schema、验证器和工具面板。创作者只能：

- 实例化白名单 Archetype；
- 修改白名单字段；
- 设置有上下限的参数；
- 连接受限规则节点；
- 使用平台提供的材质槽、模型、音效和特效；
- 通过 EditCommand 修改内容。

创作者不能：

- 上传或执行脚本；
- 调用文件系统、网络、反射和系统 API；
- 直接操作 SceneTree；
- 构造任意 RPC；
- 上传未经过重解码和转码的资源；
- 绕过预算和验证器；
- 覆盖已发布版本。

一期内容与发布规则：

- 只能引用平台内置模型、材质、音效、特效和规则节点，不允许用户上传图片、音频或 3D 文件；
- 公开 UGC 不含自由文本标题、简介和评论，只使用系统名称、词库和结构化标签；
- 技术、结构和预算验证通过后，内容在长期测试环境自动公开，不设人工前置审核；
- 发布前同步快检最多 60 秒；通过即公开，随后进入最长 10 分钟的后台抽样仿真并更新验证状态；
- 每账号同时只能运行一个验证任务，其余进入全平台公平队列；
- 发布数量、版本数量和频率不设上限；
- 结算后可给一个总体 1～5 星，并选择结构化标签，不开放文字评论；
- 一期禁止 Fork 玩家公开内容，只能从官方模板或空白内容创建；
- 普通草稿只有一个写入者；获授权的他人可只读 Preview 或复制为独立私有草稿，同账号多设备通过编辑租约互斥；
- 禁止 Fork 的范围是“他人已公开 UGC”；私有草稿复制不建立公开内容谱系；
- 每条 EditCommand 立即写本地日志，2 秒防抖上传；每 50 条命令或 5 分钟生成检查点，保留最近 30 个；
- Web 用模板和表单编辑规则；桌面端开放受限规则图，两者生成同一 Rule VM 数据；
- 创作者撤回时立即删除可下载内容、草稿和公开元数据，并终止对应运行中房间；
- 删除后只保留不可还原的 ID/哈希、删除时间、对局引用和安全审计墓碑，并按既定周期清理。

平台资产采用双轨版本：

- 视觉与音效可通过 `latest` 自动更新；
- 碰撞、占地、导航和挂点属于不可变 `GameplayAssetVersion`；
- GameplayAsset 变化必须生成新内容版本，不能伪装成运行中 P0/P1 补丁。

Schema 与规则兼容：

- 编辑器支持当前 Schema 和前两个版本自动迁移；
- 已发布 Bundle 保持可运行，安全问题除外；
- Rule VM 语义由 `ruleset_version` 固定；
- 运行时至少保留当前与上一主版本解释器，旧内容升级后重新验证。

法律边界尚未解决：一期选择自动公开，同时不设置 UGC 权利条款、测试授权或同意流程。这一状态可以用于技术原型记录，但在面向互联网开展正式公开测试或运营前属于阻断项。

# 第三部分：玩法一《机关狂奔》TRAPRUSH

## 8. 玩法定位

**1～8 人轻 3D 道具避障竞速 + 玩家推挤对抗 + 立体传送关卡工坊。**

玩家在一张由多层区块、机关、可破坏障碍和传送节点组成的地图中竞速。路线不仅向前延伸，还可以通过传送门、电梯、弹射器和切换节点在上下层与左右区块之间移动。玩家依靠走位和道具规避危险，也可以摧毁部分障碍创造捷径。

原生端与 Web 规则一致，最多 8 人；Web 只能降低特效、阴影和资源精度，不能降低房间人数或改变玩法规则。在线单人房仍使用权威服务器。

## 9. 核心体验支柱

1. **移动清楚**：玩家始终知道当前目标方向和可走路径；
2. **路线有选择**：安全路线更慢，危险路线或破坏路线更快；
3. **障碍可读**：所有危险机关都有明显预警；
4. **道具有决策**：道具既能保命，也能开路；
5. **传送有空间感**：传送能连接上、下、左、右区块，但不能让检查点失序；
6. **失败惩罚轻**：死亡或坠落主要损失时间，不直接淘汰；
7. **玩家冲突非致命**：玩家有实体碰撞、阻挡和推挤，道具可造成短眩晕、减速或有限击退，但不直接扣血；
8. **硬卡口可成立但可破局**：系统不做自动相位或防堵，允许单人封住唯一通道；所有玩家拥有低强度、长冷却的基础推击。

## 10. 视角与操作

### 10.1 视角

- 斜 45°软跟随镜头；
- 移动按世界方向映射；
- 镜头自动朝当前导航目标调整；
- 镜头只在区块切换或传送时自动调整并做短过渡；
- 多层地图使用楼层颜色、方向箭头和轮廓高亮增强可读性；
- 不依赖自由旋转镜头才能判断路线。

### 10.2 基础操作

| 操作 | PC / Web 键鼠 | 移动端触屏 |
|---|---|---|
| 移动 | WASD | 虚拟摇杆 |
| 短跳 / 自动跨小台阶 | Space | 主动作键 |
| 基础推击 | 鼠标键 / 独立键 | 推击键 |
| 使用道具 | E / 鼠标键 | 道具键 |
| 交互 | F | 交互键 |
| 重置到检查点 | 长按 R | 长按重置键 |

一期 PC/Web 不承诺手柄支持。权威运动采用直立式完整 XYZ kinematic 模型：角色可以移动和短跳，但始终直立，只允许水平朝向，不支持二段跳、攀爬、自由飞行、翻滚、墙面或天花板行走。

移动、扫掠、推挤和击退由定点 `SimulationCore` 按稳定顺序解算。Godot 物理只允许承担受控静态查询和表现，不决定竞速结果。

## 11. 地图传送与立体移动

### 11.1 地图结构

地图由可寻址区块组成：

```text
Track
├─ Segment A（中层）
├─ Segment B（上层）
├─ Segment C（下层）
├─ Segment D（左侧捷径）
└─ Segment E（右侧安全路）
```

每个区块通过普通通道或 `portal_link` 连接。传送目标可以位于：

- 同层前后区块；
- 左右平行路线；
- 上层平台；
- 下层地下区；
- 回环支路；
- 单向捷径。

### 11.2 传送规则

- 传送门必须成对或指向明确的单向出口；
- 每个出口具有稳定 ID、朝向和安全落点；
- 玩家必须经过有序检查点，传送不能跳过未完成的强制检查点；
- 传送由服务端确认，不做客户端权威预测；
- 出口被占用时等待确定性安全落点，不赋予自动相位穿透；出口外仍允许合法堵路；
- 传送链长度有上限，禁止无限循环；
- 编辑器实时显示传送连线、方向和可达性；
- 发布前验证所有必经路径至少存在一条完整通路。

UGC 权威碰撞只允许盒、球、胶囊和平台预制的少量复合体；视觉网格不参与碰撞裁决。

## 12. 障碍体系

障碍分为四类：

| 类别 | 示例 | 处理方式 |
|---|---|---|
| 固定不可破坏 | 墙、深坑、边界 | 绕行、跳跃或传送 |
| 周期机关 | 压板、摆锤、滚筒、喷火口 | 观察预警并择机通过 |
| 可破坏障碍 | 木箱、能量墙、碎石、障碍核心 | 普通攻击机制或道具削减耐久 |
| 触发型障碍 | 门、移动平台、开关链 | 交互、踩区或规则图触发 |

### 12.1 障碍破坏

- 可破坏障碍具有服务端权威 `health`；
- 玩家普通撞击不能直接摧毁障碍；
- 必须使用爆破、钻头、冲击或地图机关；
- 障碍破坏后产生明确碎裂反馈，但碎片只做表现，不进入权威物理；
- 是否重生、重生时间和重生次数由白名单参数控制；
- 破坏不得导致地图彻底不可达；
- 重要竞速门只允许状态切换，不允许永久删除。

## 13. 道具体系

以下仅作为首批原型候选，不是已锁定的正式道具表：

| 道具 | 作用 | 主要用途 |
|---|---|---|
| 护盾 | 抵消一次机关伤害或击退 | 稳定通过高危段 |
| 冲刺 | 短距离加速，不穿墙 | 抢时间 |
| 爆破球 | 对前方可破坏障碍造成高伤害 | 开路 |
| 钻头 | 短时间持续破坏接触障碍 | 连续清障 |
| 相位器 | 短时间穿过指定相位门 | 路线选择 |
| 机关脉冲 | 暂停附近周期机关一个短周期 | 控制时机 |

约束：

- 道具可造成短眩晕、减速或有限击退，但不直接扣除玩家生命；
- 连续受控后提供短暂无控保护；
- 道具拾取、使用、冷却和命中由服务端裁决；
- 道具栏数量、替换与叠加规则列入开发期决策清单，当前不锁定；
- 所有玩家的基础推击独立于拾取道具；
- 生成点和刷新间隔受内容预算限制；
- 刷新点固定可见，每局由服务端种子从该点白名单中确定道具轮换和时间；
- 小游戏端可以减少道具视觉效果，但规则不能变化。

可破坏障碍存在于共享权威世界。一名玩家摧毁后，所有玩家都能利用打开的路线；是否重生由地图受限参数决定。

## 14. 单局流程

| 阶段 | 时长规则 | 内容 |
|---|---|---|
| 内容握手 | 系统控制 | 校验基础内容哈希、补丁序列、规则版本和运行时版本 |
| 地图巡览 | 创作者白名单参数 | 展示主路线、终点或自定义目标、关键传送节点 |
| 竞速 | 创作者定义，不设内容级硬上限 | 移动、推挤、道具、避障、破坏、传送 |
| 终止判定 | 默认冲线，可组合 | 到达终点、掉出范围 N 次等白名单有界条件的与/或组合 |
| 结算 | 系统控制 | 展示本局名次、检查点、失败次数和道具使用 |

玩法内容不限制局时，但基础设施使用可续租会话：默认租约 30 分钟，有真人有效活动时续租，连续 10 分钟没有有效输入则关闭进程。有效活动必须是通过校验且改变权威状态的真人命令；心跳、重复命令、被拒命令和机器人流量不得续租。

环境失败后无限复活，返回最近检查点并承受固定复活硬直；不因生命次数淘汰。

### 14.1 排名规则

排序优先级：

1. 已冲线玩家按服务端冲线 Tick；
2. 未冲线玩家按已完成检查点数量；
3. 检查点相同时按到下一强制检查点的合法路径距离；
4. 仍相同时按更早到达当前检查点者优先；
5. 离线试玩只显示本地结算，不上传。

默认结束规则是到达终点。创作者可以使用白名单事件、变量和有界计数组合自定义结束条件，但规则图必须至少存在一个可触发终止分支。机器人在验证预算内未触发结束时只标记“未验证可完成”，不阻止自动公开。

## 15. TRAPRUSH Edit 模式

创作者可以编辑：

- 起点、终点和检查点；
- 地形块、坡道、桥、上下层区块；
- 普通通道与传送连接；
- 周期机关和触发机关；
- 可破坏障碍及耐久；
- 道具刷新点；
- 机关参数和触发链；
- 人数上限（不得超过 8）；
- 默认终点或受限自定义结束规则；
- 可选玩法时长参数，不设平台内容级硬上限；
- 表现材质槽和环境主题。

一期白名单对象建议：

```text
地形：block_static / block_slope / bridge / floor_marker
流程：spawn_grid / finish_line / checkpoint_gate
移动：platform_mover / conveyor / lift / launch_pad
传送：portal_two_way / portal_one_way / portal_switch
机关：spike / crusher / roller / flame / gate / switch
障碍：crate / energy_wall / rubble / obstacle_core
道具：pickup_shield / pickup_dash / pickup_bomb / pickup_drill
```

编辑器必须提供：

- 网格吸附与楼层切换；
- 传送连接可视化；
- 检查点顺序可视化；
- 可达性检测；
- 障碍预算和动态实体预算；
- Undo/Redo；
- 一键本地预览；
- 一键启动 1 个 Headless + 2～4 个客户端；
- 从报错直接定位到对象或规则节点。

## 16. TRAPRUSH 网络与仿真基线

| 项目 | 已确认边界 |
|---|---|
| 传输 | 原生端与 Web 一期统一 WebSocket |
| 编码 | 版本化二进制命令与快照 Schema |
| 玩家数 | 原生端与 Web 均为 1～8 人 |
| 权威数值 | 定点整数；自定义 kinematic 胶囊、扫掠与稳定顺序解算 |
| 本地预测 | 自身移动、短跳，以及与远端外推胶囊的碰撞 |
| 服务端校正 | 返回权威位置和冲量，客户端平滑对账 |
| 不由客户端裁决 | 传送、破坏、道具效果、冲线、控制效果 |
| Tick/快照频率 | 开发期根据实测决定，本稿不锁定 |
| 弱网门禁 | 香港真实样本形成前不设自动“可玩性”门禁 |

客户端只能发送：

```text
MoveIntent
JumpIntent
ShoveIntent
UseItemIntent
InteractIntent
ResetToCheckpointIntent
```

客户端不得发送最终位置、冲线结果、障碍死亡、道具命中和检查点完成断言。

网络故障正确性与手感一期只进行临时人工测试，不设固定频率或自动门禁。该选择不代表协议已经具备弱网鲁棒性；真实香港样本形成后再定义目标。若可靠传输队头阻塞被实测证明影响 TRAPRUSH，再评估原生 ENet 或 WebRTC，不能提前维护两套传输。

# 第四部分：玩法二《双塔要塞》BASTION

## 17. 玩法定位

**官方先做 1v1 / 2v2、UGC 最多 8 人的低动作塔防对战 + 赛前互设障碍 + 战场蓝图工坊。**

对局分为两个核心阶段：

1. **互设障碍阶段**：双方在预算和可达性约束下，为对手的防守区布置障碍；
2. **镜像波次防守阶段**：双方在自己的防区搭建、升级和重构炮塔体系，抵御系统向两侧生成的等价波次。

原型先验证 1v1，随后开放官方 2v2 模板。蓝图创作者可以声明每队 1～4 人、总计不超过 8 人的合法阵容，允许非对称人数，但补偿只能从平台固定预设中选择，不能自定义公式。

## 18. 核心体验支柱

1. **赛前博弈**：如何给对方制造麻烦，同时预判对方会如何针对自己；
2. **路径可读**：任何时刻都能看懂敌人从哪里来、为什么绕路；
3. **塔系组合**：单体、范围、减速、增益形成清楚的协同；
4. **低操作高决策**：每分钟约 10～25 次有效操作；
5. **体系取舍**：钱用于新建、升级、出售还是支援队友；
6. **公平约束**：障碍不能彻底封路；对称阵容预算一致，非对称阵容只能使用平台补偿预设；
7. **服务端权威**：建造、伤害、金币、寻路和胜负全部由服务端裁决。

## 19. 战场结构

标准战场包含：

```text
Team A Core
  └─ A 防守区（A 建塔，B 在赛前放障碍）
      └─ 中立连接区
          └─ B 防守区（B 建塔，A 在赛前放障碍）
              └─ Team B Core
```

每队拥有：

- 一个核心基地；
- 一条或两条合法兵线路径；
- 固定数量的建造槽；
- 一组由对方设置的障碍；
- 每名玩家的个人金币和主建造区；
- 队伍共享核心与少量公共槽；
- 每波基础收入和有上限的击杀赏金；
- 资源捐赠入口，但不能出售或拆除队友炮塔。

## 20. 互设障碍阶段

### 20.1 流程

建议采用“同时盲设、锁定后揭示”：

1. 双方各自在对手防区的障碍槽位放置障碍；
2. 对称阵容使用相同预算；非对称阵容按平台固定补偿预设分配；
3. 放置期间只能看到自己的方案，不看到对方最终方案；
4. 任一方锁定后不能继续修改；
5. 双方都锁定或倒计时结束后统一揭示；
6. 服务端重新运行可达性与预算验证；
7. 验证失败的非法放置被撤销，并退还点数；
8. 战场版本锁定，进入准备建造。

在多人队伍中，每队由一名队长实际布置，队友只能标记建议。队长先自愿申请；多人申请则队内快速投票；无人申请时随机，并允许一次主动让位。隐藏布局如何在协议层裁剪或提交属于开发期决策清单，本稿不指定实现。

### 20.2 障碍白名单

以下为首批原型候选，不是锁定的正式障碍表：

| 障碍 | 效果 | 限制 |
|---|---|---|
| 路障 | 增加单位绕行距离 | 不得完全封路 |
| 减速地块 | 降低经过单位速度 | 总覆盖长度有上限 |
| 护盾柱 | 为附近敌方来袭单位提供短时护盾 | 数量少、可被塔摧毁 |
| 分流门 | 将单位导向另一合法分支 | 必须有有效出口 |
| 干扰塔座 | 提高附近建造槽的建造成本 | 不能覆盖核心槽位 |
| 视野雾区 | 降低预警距离 | 不影响服务端锁敌 |

障碍放置属于对局准备阶段的受控 P2 拓扑修改；进入运行阶段后锁定，不能继续编辑。

任何障碍和炮塔操作都必须在提交后立即验证，任意时刻至少保留一条从出兵点到核心的合法路径；非法操作直接拒绝。障碍是否可破坏由 Archetype 决定：路径与减速类通常固定到本局结束，护盾柱等功能障碍可被系统单位或炮塔摧毁。

## 21. 炮塔体系

以下为首批原型候选，不是锁定的正式炮塔表：

| 炮塔 | 定位 | 克制 |
|---|---|---|
| 箭塔 | 低价稳定单体 | 普通单位 |
| 火炮塔 | 范围伤害、攻速慢 | 集群单位 |
| 狙击塔 | 远程高伤害 | 高血量单位 |
| 冰霜塔 | 减速控制 | 快速单位 |
| 电弧塔 | 连锁攻击 | 密集单位 |
| 增幅塔 | 增益附近友方塔 | 体系核心 |

所有炮塔：

- 只能建在白名单 `build_slot`；
- 建造、升级、出售由服务端验证；
- 完全自动瞄准和射击，玩家不接管炮塔、不控制场上角色；
- 玩家可在“最前、最近、最强、最弱”等白名单目标优先级间切换；
- 射击表现由客户端播放，伤害在服务端生效；
- 升级树一期最多 3 级；
- 不允许创作者编辑任意伤害公式，只能调有界参数。

## 22. 进攻单位与胜负

### 22.1 进攻方式

系统按相同单位类型、数量、属性、生成 Tick 和随机种子向双方生成等价波次。玩家不能主动派兵，炮塔不能跨区攻击对手塔或核心；PvP 差异只来自对手赛前布置的障碍、己方炮塔体系和经济决策。

快速兵、重装兵、集群兵、护盾兵、支援兵和首领仅作为首批原型候选。正式单位表、具体数量和属性在开发期调优，不在本稿锁定。

### 22.2 胜负条件

- 进攻单位到达敌方核心后造成核心伤害；
- 核心生命先归零的一方失败；
- 双方完成蓝图全部波次后若核心都存活，依次比较核心生命、漏怪数和完成击杀时间；
- 单局内按队伍胜负结算，再按伤害、控制、经济效率和漏兵数计算队内 MVP；
- 不产生账号级排位。

## 23. 单局流程

| 阶段 | 时长规则 | 内容 |
|---|---|---|
| 内容握手 | 系统控制 | 校验蓝图、GameplayAsset 和 Rule VM 版本 |
| 互设障碍 | 蓝图白名单参数 | 同时盲设、队长操作、预算与可达性校验、锁定 |
| 准备建造 | 蓝图白名单参数 | 使用初始金币搭建第一版塔系 |
| 镜像波次 | 创作者决定波数与局时 | 自动炮塔、建造策略、升级、出售和目标优先级 |
| 结算 | 系统控制 | 胜负、队内 MVP、塔系与经济数据 |

波数和玩法时长不设内容级上限，只受与 TRAPRUSH 相同的可续租会话和无活动回收约束。

经济由每波固定基础收入与击杀赏金组成；击杀赏金设置每波上限，避免领先方指数滚雪球。蓝图可通过白名单策略选择“全程可建、仅波间可建、波中仅升级、指定波次锁定”等建造节奏，Rule VM 只能切换策略，不能执行任意公式。

## 24. BASTION Edit 模式

# 第五部分：Edit、热修改与热发布

## 26. Edit 模式分层

项目提供三类编辑入口，但共用同一个编辑器框架：草稿、EditCommand、历史、Preview、验证和发布流程统一；TRAPRUSH 与 BASTION 只注册各自的 Schema、验证器、工具面板和可视化。

### 26.1 内部开发编辑器

- Godot Editor Plugin；
- 可访问完整白名单和调试数据；
- 支持批量生成、性能分析和验证器详情；
- 开放完整受限规则图；
- 供开发、策划、测试和 AI Agent 使用。

### 26.2 游戏内创作者编辑器

- 桌面安装版显示白名单对象、完整受限规则图和高级调试；
- 桌面 Web 只提供摆放、移动、调参、传送/路径连接、规则模板/表单和即时预览；
- Android/iOS 一期不提供编辑；
- 支持 Undo/Redo；
- 支持单人即时预览；
- 支持邀请好友进入 Preview Session；
- 不暴露文件系统和脚本。

### 26.3 对局准备编辑

- 仅 BASTION 的互设障碍阶段使用；
- 只修改当前对局 `MatchSetupState`；
- 受时间、预算、区域和可达性限制；
- 不进入内容发布系统。

## 27. 热修改等级

| 等级 | 内容 | Preview | 已开始的公开对局 |
|---|---|---|---|
| P0 表现 | 材质、音效、非权威特效 | 即时生效 | 全量下发，在安全边界生效 |
| P1 参数 | 伤害、速度、计时、耐久 | 安全边界生效 | 仅兼容白名单参数；全量下发并提示 |
| P2 拓扑 | 增删实体、移动路径、修改传送 | 安全 Tick 原子生效 | 禁止 |
| P3 规则 | 规则图和胜负逻辑 | 重编译后生效 | 禁止 |
| P4 Schema | 新组件、新命令、新节点类型 | 重启预览运行时 | 发新客户端/服务端版本 |

公开对局开局锁定不可变基础 `ContentHash`。P0/P1 不覆盖基础版本，而是形成不可变 `PatchHash` 序列；对局、结算和回放都记录基础哈希与按序应用的补丁。

## 28. 从编辑到预览

```text
UI 操作
→ EditCommand
→ AuthoringWorld
→ 增量 Schema 校验
→ 语义 / 引用 / 预算校验
→ 编译受影响子图
→ 独立 Preview 窗口或浏览器标签在安全点应用 Patch
→ 成功：生成新 Revision
→ 失败：完整回滚并定位错误对象
```

初始体验指标：

- P0/P1 修改到本地可见：目标 ≤ 3 秒；
- P2/P3 修改到单人预览：目标 ≤ 10 秒；
- 修改到 1 服 2 客户端联调：目标 ≤ 30 秒；
- 编辑器崩溃后自动恢复最近草稿；
- 每次修改都有 Revision，可撤销和比较；
- 编辑器保持打开，Preview 在独立窗口或标签运行；
- Preview 持续连接并接收 P0～P3 增量补丁，无法迁移时才自动重启；
- 多人 Preview 中作者可继续编辑并在安全点推送 P0～P3，测试者收到提示；
- Preview 永不产生正式结算、评分或在线战绩。

## 29. 热发布流水线

```text
草稿
→ 本地验证
→ Preview Session
→ 提交长期测试环境
→ 完整 Schema / 语义 / 预算验证
→ 最多 60 秒同步快检
→ 安全与资源扫描
→ 编译 SimulationBundle
→ 生成 ContentHash
→ 平台签名
→ 原子切换 latest 指针
→ 自动进入测试环境公共列表
→ 最长 10 分钟后台抽样仿真更新验证状态
```

### 29.1 热生效边界

- 已开始的公开对局锁定 `ContentId + Version + ContentHash`，另记录 P0/P1 `PatchHash` 序列；
- P2/P3 发布绝不改变运行中的公开对局，新建对局使用新版基础内容；
- P0/P1 验证通过后立即全量下发给所有对应运行中房间，不做灰度；
- P1 只在检查点/赛段切换、波次间等玩法安全边界生效，并显示版本提示；
- 技术异常由每场进程内硬阈值或 MatchHost 子进程退出检测触发自动回滚：补丁后崩溃、Tick 超预算、规则错误、非法状态或该房间连接异常；
- 平衡性问题只允许创作者或管理员手动回滚；
- 严重安全问题可以停止创建新房并终止问题对局；
- 基础内容回滚切换 `latest` 到已签名旧版本；运行中补丁回滚追加反向 Patch，不覆盖历史；
- 版本不可覆盖，只能递增；
- 回放和单局结算始终记录基础内容哈希及完整补丁顺序。

一期没有运维监控和主动告警。P1 自动回滚只能依赖 MatchServer / MatchHost 的本地硬阈值，无法感知跨房间的全局崩溃率或断线率突增，也不能依赖外部仪表盘或告警系统。

### 29.2 发布目标

- 同步技术快检目标 ≤ 60 秒；
- 基础版本激活后新房使用新版本；
- P0/P1 在运行中房间的下一玩法安全边界生效；
- 发布失败不得留下半更新状态；
- 客户端缺少资源时先下载验证，再进入房间。

### 29.3 代码热更新边界

内容热更新不等于代码热更新：

- 规则图、参数、地图和平台可信资源可以走内容管线；
- 新 GDScript、GDExtension、原生 SDK 和 Schema 变更必须发新程序版本；
- 不以 PCK 为借口绕过应用商店规则；
- 微信小游戏更新遵守微信包体和审核要求；
- AI 不得把“修改代码”伪装成“修改内容”。

# 第六部分：技术方案

## 30. 总体架构

```text
┌────────────────── 内容生产平面 ──────────────────┐
│ Godot Editor Plugin │ 游戏内 Edit │ AI Agent      │
│          ↓ EditCommand / Content Schema           │
│ Validate → Preview → Build → Sign → Auto Publish  │
└───────────────────────────────────────────────────┘
                         ↓
┌────────────────── 平台控制平面 ──────────────────┐
│ Fastify API/Auth/Content/Matchmaking/Result       │
│ sole SQLite owner │ COS │ 50 CCU FIFO            │
└───────────────────────────────────────────────────┘
                         ↓
┌────────────────── 实时接入与进程管理 ─────────────┐
│ TLS WebSocket Gateway → MatchHost                 │
│ 一局一 Godot Headless 进程 │ 可续租 │ 资源回收    │
└───────────────────────────────────────────────────┘
                         ↓
┌────────────────── 对局数据平面 ──────────────────┐
│ Client Intent → Authoritative Match Server        │
│ FixedPoint SimulationCore + Rule VM + Replay      │
└───────────────────────────────────────────────────┘
```

所有客户端只连接一个公网 TLS WebSocket 网关。网关验证一次性对局票据，并代理到内网 MatchServer 端口；Godot 子进程不直接暴露公网。网关是 Monorepo 内独立 TypeScript 服务和独立进程，与 Fastify 控制面共享鉴权契约但分离故障边界。

## 31. 三种世界

| 世界 | 用途 | 规则 |
|---|---|---|
| `AuthoringWorld` | 地图、蓝图和规则编辑 | 可变、带编辑元数据、支持 Revision |
| `SimulationWorld` | 权威仿真和客户端预测副本 | 纯数据、固定 Tick、稳定 ID |
| `PresentationWorld` | Godot 节点、动画、声音、UI | 非权威、可丢弃重建 |

禁止把 `.tscn` 直接当作 UGC 数据库。`.tscn` 只用于平台可信的表现模板；UGC 使用规范化数据格式。

- `ApplyEffect`
- `EmitGameEvent`

每条字节码指令有固定 gas 成本；空间查询按结果数收费。单图、单实体、单规则链、单 Tick 都有预算。超预算时中止该内容逻辑并生成可定位错误，不允许拖垮对局进程。

## 36. 命令模型

命令分类：

```text
PlayerCommand  玩家输入或玩法操作
EditCommand    内容编辑
AdminCommand   受权限的开发、测试和运营操作
SystemCommand  服务端内部操作
```

所有命令至少包含：

```text
command_id
actor_id
sequence
target_tick
expected_revision
content_version
payload
trace_id
```

服务端处理：

```text
鉴权
→ Schema 校验
→ 所有权校验
→ 时序与频率校验
→ 玩法语义校验
→ 排入目标 Tick
→ 事务应用
→ 产生 DomainEvent
→ 复制、回放与审计
```

## 37. 网络与回放

- 账号、草稿、内容、评分和匹配 API 使用 JSON；
- Fastify JSON Schema 是控制面契约单一事实源，并生成 OpenAPI；
- GDScript 使用生成或半生成客户端并执行契约测试；
- 所有客户端一期统一通过 TLS WebSocket 网关接入；
- 实时命令与快照使用纯 GDScript 可实现的版本化二进制 Schema，不绑定 ScenePath；
- WebSocket 的可靠有序语义是一期共同基线；实测确认队头阻塞后再立项其他传输；
- 客户端保存短期输入和状态环形缓冲；
- 回放保存命令日志、种子、基础内容哈希、P0/P1 补丁序列、运行时版本和周期关键快照；
- 相同版本、种子和输入必须得到相同关键状态哈希；
- 固定点 SimulationCore 追求跨平台可复现，但网络仍是服务器权威快照模型，不改为客户端确定性锁步；
- Godot 浮点物理与视觉节点不参与关键状态哈希。

## 38. 单区固定容量部署

一期采用最简单可控的部署：

```text
腾讯云香港长期测试环境
├─ Fastify Control Plane
│  └─ SQLite（仅此服务直接读写）
├─ TypeScript Realtime Gateway
├─ MatchHost
│  └─ 每场对局启动一个 Godot Headless 子进程
├─ COS（内容包、资源、回放）
└─ 文件 / 结构化日志
```

规则：

- 不跨区；
- 不做自动扩缩容；
- 按 50 CCU 固定容量设计；
- 一场对局一个进程，避免 UGC 异常影响其他房间；
- MatchHost 分配内网端口、限制资源、处理租约并回收；
- 默认会话租约 30 分钟；只有通过校验并改变权威状态的真人命令可续租，连续 10 分钟无此类输入则关闭；
- 容量满时进入 FIFO 队列并显示预计等待时间；
- 编辑但未进入对局的用户不占 MatchServer 名额；
- 支持快速游戏与房间码；
- 不做技能匹配；
- 不做观战连接；
- 回放数据先存储，播放 UI 二期再做；
- 每场对局进程异常时尽力保留最后关键快照和日志；
- SQLite 是测试期方案，PostgreSQL 为产品化迁移目标；
- 网关、MatchHost 和 Godot 不得直接访问 SQLite，只能调用控制面 API 或提交事件；
- 不做备份、主动可用性探测、仪表盘和告警。

1. 先读项目现有代码，再生成代码；

15. AI 资产不强制保存模型、提示词、种子或来源；收到权利投诉时由人类逐案判断是否下架或替换；

## 47. AI 多角色建议

始终由一个主 Agent 统筹。子 Agent 只在互不重叠的模块或独立工作区并行，禁止同时修改同一场景、Schema 或协议。必要时按任务临时分工：

# 第九部分：测试与质量方案

## 48. 测试原则

优先级：

```text
权威正确性
> UGC 安全
> 可回放与可复现
> Edit / Hot Publish 可靠性
> 网络鲁棒性
> 性能
> 表现质量
```

AI 生成代码必须比普通手写代码有更强的自动化证据，因为其产出速度更快，也更容易快速放大错误。

测试强度采用不对称策略：

- 仿真、命令、Schema、Rule VM、内容编译和热发布坚持测试先行；

- 不建立自动性能回归门禁，出现明显问题后再分析优化；
- 纵向切片期间不组织外部真人试玩，由项目负责人按清单签署玩法结论。

# 第十部分：项目初始执行宪法

## 53. 宪法 v1

以下内容应在项目初始化时同步写入根目录 `AGENTS.md`，作为所有人类和 AI Agent 的最高工程规则。

### 第一条：范围优先

一期只做本文列出的纵向切片。任何新增系统必须说明它服务于哪个一期验收项，否则延期。

### 第二条：服务器唯一权威

位置确认、命中、道具效果、障碍破坏、金币、建造、伤害、冲线和胜负均由服务端裁决。客户端只提交意图。

### 第三条：UGC 永远不可信

任何来自客户端、创作者、AI 和外部文件的内容都必须经过 Schema、语义、预算、安全和仿真验证。

### 第四条：UGC 是数据，不是代码

禁止玩家上传或执行 GDScript、C#、GDExtension、原生库和任意 PCK。规则表达只能使用白名单 Rule VM。

### 第五条：仿真与表现分离

`SimulationWorld` 不依赖 SceneTree，核心数值使用定点整数；Godot Node 只负责输入适配、受控查询和表现映射。禁止把 Node 或 Godot 浮点物理当作权威数据库。

### 第六条：版本不可变

已发布基础内容不可覆盖，只能发布新版本。公开对局开局锁定基础内容哈希，运行中不得替换 P2/P3；P0/P1 必须以不可变补丁序列在玩法安全边界应用并进入回放。

### 第七条：客户端技术栈固定

使用 Godot 4.7 Standard + GDScript。禁止创建 `.cs` / `.csproj`。Compatibility 是共同渲染基线。共享玩法与编辑核心禁止 GDExtension；平台适配层只有在 Web 存在空实现时可例外。

### 第八条：先验证再优化

先实现服务器权威、定点仿真和正确回放，再加入预测；出现可观察瓶颈后再做复杂优化。不得把 GDExtension 引入共享核心。

### 第九条：小步可验证

每个任务必须有明确输入、输出和验收测试。一次变更只解决一个主要问题，禁止无关重构。

### 第十条：测试是完成条件

AI 或人类不能以“实现完了”代替测试证据。没有执行结果的测试等于没有测试。

### 第十一条：AI 不得猜 API

不确定的 Godot API 必须查 4.7 官方文档或项目内已验证用法。禁止生成 Godot 3 语法。

### 第十二条：场景修改必须可撤销

大型 `.tscn` 修改优先通过 MCP、Editor API 和 UndoRedo。禁止无上下文地重写整个场景文件。

### 第十三条：热发布必须可回滚

任何内容激活都必须保留上一签名基础版本。P0/P1 全量运行时补丁必须能由进程内技术阈值自动回滚；禁止原地覆盖。

### 第十四条：离线结果永不回写

离线模式不发结算写请求。恢复在线后也不补传离线战绩和奖励。

### 第十五条：单局排名不扩张

一期只提供单局名次和 MVP。任何 MMR、段位、赛季、长期排行榜需求必须重新立项。

### 第十六条：单区固定容量

一期不引入跨区、弹性扩容和观战。香港长期测试环境按 50 CCU 设计，容量不足时进入 FIFO 队列。一局一 Headless 进程，由 MatchHost 续租和回收。

### 第十七条：性能有预算

实体数、规则 gas、查询次数、包体和单任务资源必须有安全上限，超限 UGC 在发布前拒绝。工程性能数值当前只作观察参考，不得虚构为自动回归门禁。

### 第十八条：高风险操作需要人类门禁

以下操作必须由人类确认：

- Schema 破坏性变更；
- 网络协议不兼容变更；
- 数据删除和迁移；
- 新依赖和许可证；
- 安全边界变化；
- AI 发起的提交、推送、部署、发布或回滚；
- 管理员终止对局；
- 项目范围和平台变更。

### 第十九条：文档随代码变化

命令、Schema、规则节点、目录、运行方法和验收标准变化时，同一任务必须更新对应文档。

### 第二十条：可解释性优先

人类无法理解、AI 无法解释、测试无法证明的实现不得进入主线。

### 第二十一条：数据库单一所有者

一期只有 Fastify 控制面可以直接读写 SQLite。网关、MatchHost 和 Godot MatchServer 必须通过 API 或事件交互，为后续 PostgreSQL 迁移保留边界。

### 第二十二条：公网进程不直连

客户端只能连接 TLS WebSocket 网关。Godot MatchServer 使用内网临时端口，不直接暴露公网。

### 第二十三条：类型严格度分区

`shared/`、`simulation/`、`ugc/`、`server/` 必须静态类型且警告视为错误；UI 和工具层可有限使用 `Variant`，进入核心边界前必须完成 Schema 校验。

### 第二十四条：测试声明必须真实

网络故障测试是临时人工检查，性能值是观察参考，外部真人测试尚未执行。任何 AI 或人类不得把这些内容表述为稳定自动门禁或已验证能力。

### 第二十五条：测试环境风险不等于产品能力

开放注册、无注册保护、公开未过滤用户名、自动公开 UGC、无主动作弊处置、无监控、无备份和无 UGC 授权条款均为当前明确风险。正式公开运营前必须重新立项评审，不能因原型能运行而默认沿用。

## 54. 决策优先级

发生冲突时按以下顺序裁决：

```text
安全与权威正确性
> 当前版本内的数据一致性与可回滚
> 可复现与可测试
> 已拍板产品范围
> 迭代速度
> 性能优化
> 视觉效果
```

该顺序不能自动覆盖本文明确记录的风险接受项；若新实现与风险接受项冲突，必须由人类重新拍板，而不是由 AI 自行“修正”产品决策。

# 附录 A：首个可运行验收场景

本附录定义内部固定测试夹具，不限制创作者内容的局时、波数或人数配置。

## A.1 TRAPRUSH

一张 90 秒赛道必须包含：

- 起点和终点；
- 3 个顺序检查点；
- 1 个向上层传送；
- 1 个向左或向右区块传送；
- 1 个周期障碍；
- 1 个可破坏障碍；
- 1 个爆破道具；
- 1 个安全路线和 1 个危险捷径；
- 2 人 Headless 对局；
- 单局名次结算。

## A.2 BASTION

一张 5 分钟战场必须包含：

- 双方核心；
- 双方各一条合法路径；
- 双方各 3 个障碍槽；
- 互设障碍阶段；
- 3 种塔；
- 3 种兵；
- 建造、升级、出售；
- 核心伤害与胜负；
- 单局队伍结算和 MVP。

# 附录 B：第一批测试用例

1. 传送门 A→B 后不能跳过强制检查点；
2. A→B→A 循环在发布前被发现；
3. 爆破球只能伤害 `destructible`；
4. 障碍重生不会把玩家卡入模型；
5. 客户端伪造冲线被拒绝；
6. 离线冲线结果没有网络写请求；
7. BASTION 路障不能封死唯一路径；
8. 对称阵容障碍预算一致；非对称阵容只能应用平台补偿预设；
9. 客户端伪造金币被拒绝；
10. 同一建造槽并发建塔只有一个成功；
11. P2/P3 新内容版本不改变运行中的旧房，P0/P1 补丁按安全边界生效；
12. `latest` 回滚后新房加载旧签名版本；
13. Rule VM 超 gas 时只中止问题规则；
14. 断线重连后客户端恢复权威快照；
15. 相同回放得到相同关键状态哈希。

# 附录 C：术语

| 术语 | 定义 |
|---|---|
| AuthoringWorld | 可编辑的创作数据模型 |
| SimulationWorld | 权威纯数据运行世界 |
| PresentationWorld | Godot 表现节点世界 |
| EditCommand | 对创作内容的可审计修改命令 |
| Preview Session | 允许快速热修改的测试会话 |
| Published Match | 内容版本锁定的公开对局 |
| SimulationBundle | 编译、验证和签名后的运行内容 |
| ContentHash | 某一不可变内容版本的字节哈希 |
| PatchHash | 运行中对局按顺序应用的不可变 P0/P1 补丁哈希 |
| Rule VM | 执行受限规则图的虚拟机 |
| gas | 规则执行预算 |
| 单局排名 | 只在当前对局内产生的名次或 MVP，不形成长期段位 |
