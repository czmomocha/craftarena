## 1. 玩法定位

**官方先做 1v1 / 2v2、UGC 最多 8 人的低动作塔防对战 + 赛前互设障碍 + 战场蓝图工坊。**

对局分为两个核心阶段：

1. **互设障碍阶段**：双方在预算和可达性约束下，为对手的防守区布置障碍；
2. **镜像波次防守阶段**：双方在自己的防区搭建、升级和重构炮塔体系，抵御系统向两侧生成的等价波次。

原型先验证 1v1，随后开放官方 2v2 模板。蓝图创作者可以声明每队 1～4 人、总计不超过 8 人的合法阵容，允许非对称人数，但补偿只能从平台固定预设中选择，不能自定义公式。

## 2. 核心体验支柱

1. **赛前博弈**：如何给对方制造麻烦，同时预判对方会如何针对自己；
2. **路径可读**：任何时刻都能看懂敌人从哪里来、为什么绕路；
3. **塔系组合**：单体、范围、减速、增益形成清楚的协同；
4. **低操作高决策**：每分钟约 10～25 次有效操作；
5. **体系取舍**：钱用于新建、升级、出售还是支援队友；
6. **公平约束**：障碍不能彻底封路；对称阵容预算一致，非对称阵容只能使用平台补偿预设；
7. **服务端权威**：建造、伤害、金币、寻路和胜负全部由服务端裁决。

## 3. 战场结构

```text
Team A Core
  └─ A 防守区（A 建塔，B 在赛前放障碍）
      └─ 中立连接区
          └─ B 防守区（B 建塔，A 在赛前放障碍）
              └─ Team B Core
```

每队拥有：

- 一个核心基地；
- 一条或两条合法兵线路径；
- 固定数量的建造槽；
- 一组由对方设置的障碍；
- 每名玩家的个人金币和主建造区；
- 队伍共享核心与少量公共槽；
- 每波基础收入和有上限的击杀赏金；
- 资源捐赠入口，但不能出售或拆除队友炮塔。

## 4. 互设障碍阶段

### 4.1 流程

采用"同时盲设、锁定后揭示"：

1. 双方各自在对手防区的障碍槽位放置障碍；
2. 对称阵容使用相同预算；非对称阵容按平台固定补偿预设分配；
3. 放置期间只能看到自己的方案，不看到对方最终方案；
4. 任一方锁定后不能继续修改；
5. 双方都锁定或倒计时结束后统一揭示；
6. 服务端重新运行可达性与预算验证；
7. 验证失败的非法放置被撤销，并退还点数；
8. 战场版本锁定，进入准备建造。

在多人队伍中，每队由一名队长实际布置，队友只能标记建议。队长先自愿申请；多人申请则队内快速投票；无人申请时随机，并允许一次主动让位。

隐藏布局如何在协议层裁剪或提交**未锁定**，列入 [CD-63](../60-plan/63-open-decisions.md)。

### 4.2 障碍白名单（首批原型候选）

以下**不是**锁定的正式障碍表。

| 障碍 | 效果 | 限制 |
|---|---|---|
| 路障 | 增加单位绕行距离 | 不得完全封路 |
| 减速地块 | 降低经过单位速度 | 总覆盖长度有上限 |
| 护盾柱 | 为附近敌方来袭单位提供短时护盾 | 数量少、可被塔摧毁 |
| 分流门 | 将单位导向另一合法分支 | 必须有有效出口 |
| 干扰塔座 | 提高附近建造槽的建造成本 | 不能覆盖核心槽位 |
| 视野雾区 | 降低预警距离 | 不影响服务端锁敌 |

### 4.3 合法性约束

- 障碍放置属于对局准备阶段的受控 P2 拓扑修改；进入运行阶段后锁定，不能继续编辑；
- 任何障碍和炮塔操作都必须在提交后立即验证，任意时刻至少保留一条从出兵点到核心的合法路径；非法操作直接拒绝；
- 障碍是否可破坏由 Archetype 决定：路径与减速类通常固定到本局结束，护盾柱等功能障碍可被系统单位或炮塔摧毁。

## 5. 炮塔、波次与胜负

### 5.1 炮塔体系（首批原型候选）

| 炮塔 | 定位 | 克制 |
|---|---|---|
| 箭塔 | 低价稳定单体 | 普通单位 |
| 火炮塔 | 范围伤害、攻速慢 | 集群单位 |
| 狙击塔 | 远程高伤害 | 高血量单位 |
| 冰霜塔 | 减速控制 | 快速单位 |
| 电弧塔 | 连锁攻击 | 密集单位 |
| 增幅塔 | 增益附近友方塔 | 体系核心 |

所有炮塔：

- 只能建在白名单 `build_slot`；
- 建造、升级、出售由服务端验证；
- 完全自动瞄准和射击，玩家不接管炮塔、不控制场上角色；
- 玩家可在"最前、最近、最强、最弱"等白名单目标优先级间切换；
- 射击表现由客户端播放，伤害在服务端生效；
- 升级树一期最多 3 级；
- 不允许创作者编辑任意伤害公式，只能调有界参数。

### 5.2 进攻单位与胜负

系统按相同单位类型、数量、属性、生成 Tick 和随机种子向双方生成等价波次。玩家**不能主动派兵**，炮塔不能跨区攻击对手塔或核心；PvP 差异只来自对手赛前布置的障碍、己方炮塔体系和经济决策。

快速兵、重装兵、集群兵、护盾兵、支援兵和首领仅作为首批原型候选。正式单位表、具体数量和属性在开发期调优，见 [CD-63](../60-plan/63-open-decisions.md)。

胜负条件：

- 进攻单位到达敌方核心后造成核心伤害；
- 核心生命先归零的一方失败；
- 双方完成蓝图全部波次后若核心都存活，依次比较核心生命、漏怪数和完成击杀时间；
- 单局内按队伍胜负结算，再按伤害、控制、经济效率和漏兵数计算队内 MVP；
- 不产生账号级排位。

## 6. 单局流程

| 阶段 | 时长规则 | 内容 |
|---|---|---|
| 内容握手 | 系统控制 | 校验蓝图、GameplayAsset 和 Rule VM 版本 |
| 互设障碍 | 蓝图白名单参数 | 同时盲设、队长操作、预算与可达性校验、锁定 |
| 准备建造 | 蓝图白名单参数 | 使用初始金币搭建第一版塔系 |
| 镜像波次 | 创作者决定波数与局时 | 自动炮塔、建造策略、升级、出售和目标优先级 |
| 结算 | 系统控制 | 胜负、队内 MVP、塔系与经济数据 |

波数和玩法时长不设内容级上限，只受与 TRAPRUSH 相同的可续租会话和无活动回收约束，见 [CD-44](../40-technical/44-deployment.md)。

经济由每波固定基础收入与击杀赏金组成；击杀赏金设置每波上限，避免领先方指数滚雪球。蓝图可通过白名单策略选择"全程可建、仅波间可建、波中仅升级、指定波次锁定"等建造节奏，Rule VM 只能切换策略，不能执行任意公式。

## 7. Edit 模式

正式蓝图编辑与单局互设障碍是两个不同层级。

### 7.1 蓝图编辑

创作者可以编辑：

- 战场尺寸；
- 兵线路径和分支；
- 障碍槽位；
- 建造槽位；
- 双方核心位置；
- 波次基础表；
- 初始金币、基础收入、击杀赏金上限和时限；
- 可用塔、兵和障碍白名单；
- 规则图中的胜负与阶段触发；
- 表现主题；
- 每队 1～4 人、总计最多 8 人的合法阵容；
- 平台提供的非对称人数补偿预设。

创作者只能选择白名单塔、单位和障碍原型，并在平台上下限内调整倍率；总威胁、经济和性能预算必须通过验证，不开放任意公式。

### 7.2 单局互设障碍

- 只能使用蓝图预留的障碍槽；
- 只能在准备阶段操作；
- 使用固定点数；
- 不产生新的内容版本；
- 作为该场对局的 `MatchSetupState` 保存；
- 进入运行阶段后不可修改；
- 回放必须记录完整障碍布置命令。

### 7.3 运行阶段建塔

运行阶段建塔是玩法命令，不是内容热更新。它只修改当前对局状态：

```text
BuildTowerIntent
UpgradeTowerIntent
SellTowerIntent
SetTowerPriorityIntent
DonateResourceIntent
```

## 8. 网络与仿真基线

| 项目 | 已确认边界 |
|---|---|
| 传输 | 原生端与 Web 一期统一 WebSocket |
| 编码 | 版本化二进制命令与快照 Schema |
| 玩家数 | 蓝图声明；每队 1～4 人，总计最多 8 人 |
| 客户端预测 | 玩法命令不预测，等待服务端确认 |
| 寻路 | 离散 waypoint/边图；障碍启用、禁用或修改边成本 |
| 权威数值 | 定点整数；确定性图搜索、经济、锁敌和伤害顺序 |
| Tick/快照频率 | 开发期根据实测决定，本文不锁定 |
| 实体预算 | 作为观测与 UGC 安全上限逐步实测，不作为当前发布性能承诺 |

客户端不得提交金币、塔伤害、单位死亡、核心伤害和胜负结果。
